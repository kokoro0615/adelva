## Post-audit correction pass (2026-08-31)

The independent `gpt-5.6-sol` / `xhigh` live-browser audit returned four
unresolved defects against the local production build. Each was reproduced in a
real browser before any edit, root-caused to a proven mechanism, covered by a
test that fails on the pre-fix build, and then fixed.

### 1 — HIGH: reduced-motion menu focus never entered the dialog (`/`, all viewports)

- **Observed** Under `prefers-reduced-motion: reduce`, opening the menu left focus on `Menu` (390) or `Journeys` (768/1440). Under `no-preference` focus landed on `Close` correctly.
- **Root cause (proven)** `transition-property` initialises to `all`, so the reduced-motion fallback's blanket `transition-duration: 40ms !important` on `*` did not only shorten authored transitions — it _created_ one on every element for every animatable property, inherited `visibility` included. A traced `HTMLElement.focus()` recorded the panel resolving `visibility` over 40ms instead of the authored `0s`, and the `.menu__close` control — which authors no transition at all under `reduce` — still computing `visibility: hidden` for two further frames while it resolved the inherited step. `focus()` is a silent no-op on a hidden element, so the one-shot call was refused and no error surfaced.
- **Fix** `src/app/globals.css`: under `reduce`, `.menu`, `.menu *` and `.menu-backdrop` resolve `transition-duration: 0s`. Presence is state, not decoration, so nothing inside a modal can become focusable a frame later than it becomes visible. The final acceptance correction below supersedes the earlier bounded retry in `src/components/site-header.tsx` with an exposure-conditioned lifecycle.
- **Evidence** Traced `focus()` calls before/after: 3 attempts with `landed: false, false, true` under `reduce` → 1 attempt, `landed: true`, under both preferences. Focus trap, Escape dismissal and focus restoration are asserted in the same tests and unchanged.

### 2 — MEDIUM: incomplete scroll lock (`/`, all viewports and preferences)

- **Observed** With the menu open, `window.scrollTo(0, 700)` moved the document to 700 and left it there, although `data-scroll-locked="true"` was set. Wheel and PageDown were correctly blocked.
- **Root cause (proven)** The lock was `html[data-scroll-locked] { overflow: hidden }` plus a Lenis pause. `overflow: hidden` only stops _user_ scrolling; an overflow-clipped viewport stays programmatically scrollable, so `window.scrollTo`, `scrollIntoView`, a hash jump or any script could still slide the page behind the open dialog. Confirmed by reading `getComputedStyle(html).overflow === "hidden"` while `scrollY` reported 700.
- **Fix** `src/lib/motion.ts`: `lockScroll()` now records the exact `scrollX`/`scrollY` at acquisition and re-pins the document from a passive `scroll` listener whenever anything moves it, using `behavior: "instant"` so the correction is never animated by the `scroll-behavior: smooth` this document sets under `no-preference`. Release removes the listener, closes any same-frame gap, and only then resumes the pause handlers. The document keeps its full height and position throughout — no `position: fixed` body, no compensating offset — so the lock stays layout stable. `src/components/scroll-provider.tsx`: Lenis re-syncs to the actual document position on resume instead of restarting from the target it was carrying when it was stopped.
- **Evidence** Programmatic scroll, `scrollIntoView`, wheel, PageDown and End all hold the position at 400 across 3 viewports × 2 preferences; `document.body` top offset, `scrollHeight` and `clientWidth` are identical before and during the lock; the exact position survives close, after which native scrolling resumes.

### 3 — MEDIUM: first-viewport content was motion-gated (`/`, `no-preference`)

- **Observed** At first paint the H1, lede and cue were `opacity: 0`, and the H1 sat outside the viewport entirely: `y 880–947` at 390×844 and `y 1042–1156` at 768×1024, settling only after ~1.1–1.6 s.
- **Root cause (proven)** The hero entrance animated `opacity: 0 → 1` together with a `translateY` of `--hero-rise: clamp(4.5rem, 16vh, 11rem)` — 135px at 390×844 and 164px at 768×1024 — under `animation-fill-mode: both`, so the `from` state was painted on the first frame. The hero body has only 32px of footwell, so any travel of that size necessarily started below the fold.
- **Fix** `src/app/globals.css`: `field-rise`, `monument-rise` and `field-fade` are replaced by a single transform-only `field-settle` of `--hero-settle: 0.75rem`. The opacity ramp is gone entirely and the travel is smaller than the shallowest hero footwell (`--gutter`, 20px), so every element is painted at full opacity, at final size, inside the viewport, on the first frame. The measured curve, the staged delays and the 1.4s monument duration are kept, as is the decorative plate settle behind it.
- **Evidence** First-paint probe from document start, `no-preference`: `opacity 1` and a 12px settle at frame 2–3 (~67–74ms) at all three viewports, H1 bottom `880/900`, `1004/1024`, `824/844`. A deterministic complement seeks each entrance to 0%, 25% and 60% of its own timeline and asserts the same, so a slow harness cannot turn a settled page into a pass.

### 4 — MEDIUM: tablet brand clipping (`/`, 768×1024)

- **Observed** The masthead identity rendered as `ANTARCTIC FIELD N…`: `clientWidth 180` against `scrollWidth 205`.
- **Root cause (proven)** Measured bar geometry at 768: a 728px bar whose fixed siblings consumed 513.66px (327.13px tab row + 87.28px Rates + 99.25px Enquire), leaving the `flex: 1 1 auto` brand 196.34px, or a 180.34px content box for a 205px wordmark. The tab row's `padding-inline: 1.5rem` contributed 144px of that, and the brand's `overflow: hidden` + `text-overflow: ellipsis` guard then elided the identity rather than overflowing.
- **Fix** `src/app/globals.css`: from the 48rem breakpoint the tab padding is fluid, `clamp(0.9rem, 1.9vw, 1.5rem)`. It returns to the measured `1.5rem` at 1263px and holds it through 1440, so the measured desktop geometry is byte-identical and only the genuinely crowded range tightens. The wordmark's own type metrics, the lockup and the 390 compact variant are untouched, and the ellipsis guard is retained as a last resort against overflow.
- **Evidence** 768 now measures `clientWidth 205 / scrollWidth 205` with no ellipsis; 1440 unchanged at `205 / 205`; 390 keeps the compact lockup at `108 / 108`. The masthead bar does not overflow and the document gains no horizontal scrollbar at any of the three viewports. Tabs stay at their measured 40px height and far above the 24px target-size floor.

Only the curve and staging are reproduced; the travel is now a 12px settle and the opacity ramp is dropped. The final correction below independently restores the measured settled geometry.
- **Tablet tab padding** The measured `1.5rem` tab padding is preserved from 1263px to 1440px and compressed below that. The measured desktop numbers are unaffected; the 768 header is authored to fit the approved identity rather than elide it.
- **Reduced-motion menu presence** The authored 40ms reduced-motion state feedback still applies site-wide, but the two surfaces gated on `visibility` resolve instantly. A modal that is painted must be focusable in the same frame.
- **`tests/e2e/visual.spec.ts-snapshots/home-tablet-chromium-linux.png` regenerated.** The rendered tablet result genuinely changed. The diff is 2236 px (ratio 0.01), bounded to `x 36–532, y 21–66` — entirely inside the 48px masthead bar — and is the tighter tab row plus the un-elided wordmark. The desktop and mobile goldens are byte-identical (`md5` unchanged) and were not regenerated.

### Incidental observation, not fixed (outside this scope)

A CSS-smooth programmatic scroll issued inside the first ~300 ms after load is cancelled by the font-ready `ScrollTrigger.refresh()` in `MotionStage`, which saves and restores the scroll position. Verified as user-harmless: an early user wheel scroll holds at 500 and an early `behavior: "instant"` scroll holds at 400 at both 1440 and 390; only an in-flight smooth-scroll _animation_ in that window is dropped. Recorded rather than changed, since it is outside the four audited findings.

## Final acceptance audit corrections (2026-08-31)

The independent final audit found three remaining acceptance defects after the
historical four-finding correction pass. Each correction below is covered by a
browser regression that failed against the pre-fix production build.

### Home stage and monument

- **Root cause** Home inherited the generic `.hero--full` `100svh` minimum and its
  title width formula reduced the tablet font size to fit before MonumentFit
  applied a second face compensation. The result was a one-viewport stage and a
  135/113.5px tablet H1 instead of the measured 256/256px landmark.
- **Correction** `.hero--anchor.hero--full` is exactly `200svh`; its media, scrim
  and body are CSS-sticky `100svh` layers. ScrollTrigger reads the measured stage
  height on refresh. The H1 keeps 256/256 above mobile and 80/80 on mobile,
  separates resolved-face compensation from responsive stage scale, and retains
  the opacity-one 12px settle.
- **Acceptance geometry** Hero height is 1800/2048/1688px; desktop H1 spans
  x=137.6–1302.3, tablet is x=81.7, y=744, w=604.7, h=256, and mobile is about
  366px wide. Browser tests also require zero document horizontal overflow and
  meaningful midpoint-to-end scrub progression.

### Shared itinerary-detail H1 role

- **Root cause** `buildJourney()` selected `titleStyle: "serif"`, while the false
  evidence record below claimed the target was upright uppercase.
- **Correction** Every journey produced by the shared builder uses
  `serif-italic`: title case, italic, 60/60 at desktop/tablet and 32/32 mobile.
  The browser regression iterates every shared-builder document at all three
  viewports.

### Menu focus exposure and release geometry

- **Root cause** React open state and CSS visibility become true before the
  transform wipe exposes Close. The old focus call therefore succeeded while
  the label and focus ring were still offscreen under normal motion.
- **Correction** Reduced motion focuses immediately. Normal motion checks the
  Close rectangle plus its 6px focus-outline clearance against both the viewport
  and the moving `overflow: hidden` menu rectangle on each animation frame. It
  focuses on the first fully exposed frame and cancels the rAF on close/unmount;
  no transition event or duration gates the transfer. Early Tab uses the same
  predicate and cannot focus the obscured control. Escape, trap, opener
  restoration, scroll lock and reopen are retained.
- **Release hardening** The longer page exposed a queued End/native/Lenis target
  after unlock. Final release now always issues the held instant coordinates
  before resuming scroll handlers, cancelling a pending target even when the
  current frame still reports the held position.
