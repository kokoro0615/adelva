## 2. 変更点

コミット：`b31d4e9`（描き方とエンジン）、`55890a5`（映像）、`8e40c68`（残りの読み取り・e2e）、`2e79179`（署名の経路の標本化）、`6357321`（低い画面の手紙）、`2281a76`（静止版の帯）。

**エンジン（`engine.ts`）**

- スマホは「減衰した進度」で動く：`window.scrollY` を時定数 60 ms の指数追従（フレーム時間に依存しない式）で追い、
  0.3 px 以内で一致させる。iOS の不規則なスクロール値が段差として見えない。1.5 画面を超える跳び（アンカー移動など）は即座に合わせる。
- スクロール位置はスマホでは passive の scroll イベントで読む（フレーム内では読まない）。PC は Lenis と同じ ticker 内で従来どおり読む（減衰なし）。
- ループは止まる：位置が落ち着き、どの場面も次のフレームを求めなければ ticker から外れ、scroll・resize・`invalidate()` で再開。
- ヘッダーの面（film / paper / glass）は計測済みの場面の位置から決める（毎フレームの `getBoundingClientRect` をやめた）。

**スマホの場面（`mobile.ts`・`home.module.css`・`home-page.tsx`）** — 毎フレーム書くのは transform と opacity だけ

- 一本の線：`height` と `mask-image` の書き換えをやめ、1 つの transform で置いて回す入れ物と、その中で scaleY する 2 本の線分にした（切れ目は 2 本の間）。
- 支援対象の 2 枚：`--s` による `height/top` と `clip-path` をやめ、「上端を動かす外箱」と「下端を動かす内箱」（どちらも translate だけで切り抜く）
  と、写真・陰り・カードをステージ座標に戻す枠、の入れ子にした。陰りは見えている範囲の高さに scaleY。
- 支援領域の 3 つの帯：`left/top/width/height` と画像の `width/height` をやめ、同じ入れ子の窓（2 次元）＋固定サイズの画像を 1 つの transform で置く。
  ラベルは `top` → translate、継ぎ目は `left/top/width` → translate＋scaleX。
- 形の読み取り（ヘッダーのロゴ・目的の文章・課題のレール・カードの折り畳み高さ・ラベル高さ・署名の箱・映像の canvas・落ちる 6 語）は
  開始時・リサイズ時・フォント読み込み時だけ。ヘッダーがコンパクトになったときはロゴを 1 回読み直す。署名のペン先の経路は最初に 2 単位刻みで標本化。
- 場面の根元に書いていたカスタムプロパティ（`--po`・`--ho`・`--so`・`--vo`・`--io`・`--co`・`--go`・`--fo`）は、使う要素の opacity に直接書く（子孫全体のスタイル再計算をなくす）。
- 課題の道のりの点・工程の目盛りの点灯は 0.28〜0.32 s で切り替わる。湖の上の工程札と最後のリンクはスマホでは blur なしの燻した塗り（コントラストは測定済み）。
- 映像の一時停止ボタンはスマホでも 44 px（40 px だった）。

**WebGL（`gl.ts`）**

- 写真は `createImageBitmap` でメインスレッド外でデコードし、1 フレームに 1 枚ずつ GPU へ送り、送った後はデコード済みのコピーを閉じる
  （変更前は湖の 8 枚を `onload` の 1 タスクで同期デコード＋転送していた）。
- パノラマと湖はスクロールしたときに描き、止まっている間は霧・水・湯気・暖簾が動く分だけ 24 fps で描く。canvas の大きさは ResizeObserver から。
- スマホではパノラマと湖を同時に GPU に置かない：パノラマはページ上端から課題の 1 画面先まで、湖は支援の進め方の 3 画面手前から。範囲を 1 画面以上離れると
  テクスチャを解放し、戻ると再読み込みする（検証用の `?capture` は両方を保持）。湖はスマホでは近づくまで読み込まない。

**映像（`assets.ts`・`page.tsx`）**

- 1024 px 未満は専用の 720p エンコード（縦 720×1280・横 1280×720、H.264 High@4.0、2.4 Mbps 2 パス、キーフレーム 2 秒以内、9.5 MB）。PC が選ぶファイルは不変。
- `preload="metadata"`。再生はモーションが「映像が見えている」ときに始める。縦持ちのスマホは縦映像の最初のフレームをポスターにし（その媒体だけ preload）、再生開始で絵が跳ばない。
- 映像の 2 つの半分（分かれる演出）は、映像に新しいフレームが来たときだけ描き直す。

**空白の画面をなくす（文言・順序は不変）**

- 線の切れ目は、ステージが流れ出すと文章と一緒に上へ動く（線は残り、文章には重ならない）。
- 目的の文章が線を通り過ぎた時点で、支援対象の線が引き継いで水平に回り、紙の中央に乗ったまま上がってくる。2 つの見出しはステージが着く前から線の上下に上がる
  （変更前は着いてから。約 150 px 早い）。導入の段落は着いた直後に出る。
- 創業者の手紙の引用符と文字、支援の進め方の導入文と見出しは、ステージが画面に入ってくる途中から書き出す。

## 6. 決定事項

- **減衰は電話だけ（時定数 60 ms）**。PC は Lenis がホイールを既に滑らかにしているので減衰しない（二重の遅れを避ける）。1.5 画面を超える跳びは即座に合わせる（途中の場面を一瞬通過させない）。
- **静止中の WebGL は 24 fps**。霧・湯気・暖簾・水面の文字の揺れ・粒子感は止めず（承認済みの「生きている写真」）、映像と同じ 24 fps で描く。スクロール中は毎フレーム。PC は従来どおり毎フレーム。
- **電話の映像は 720p・2.4 Mbps**。810×1440・2.7 Mbps と比べ、1080×1920 に拡大した SSIM は 0.9775 対 0.9786 と差が小さく、元の情報量（約 244×432）から見ても 720p で十分。
  x264 の `mbtree` を切り `ipratio` を 1.1 に下げて、2 秒ごとのキーフレームで質感が脈打つ現象（AV1 で本番に出た問題）を半分にした（キーフレームでの SSIM の跳び 0.0079 → 0.0043）。
  横持ちの電話（1024 px 未満の横向き）にも同じ条件の 1280×720 を用意し、PC 用 47 MB を電話に送らない。
- **映像の `poster` 属性を外した**。属性は画面の向きで切り替えられないため、下に敷いた `<picture>`（縦持ちの電話は縦映像の 1 フレーム目）が最初の絵になる。
- **一つのテクスチャ群だけを GPU に置く**のは電話だけ。PC は両方を保持（従来どおり、読み戻し試験も）。`?capture`（検証）は電話でも両方を保持。
- **契約の 64 MB には届いていない**（湖は単独で約 104 MB）。湖の板を電話のカメラが見る横幅に切り詰める案は、タブレット横向き（< 1024 px）でほぼ全幅が要るため、
  端末別のファイルが必要になる。今回は「同時に持たない」「CPU 側のデコード済みコピーを閉じる」までにした（§8）。
- **工程の目盛りの長さの遷移は幅のまま**（6 本・高さ 1 px）。transform にすると隣の目盛りに重なるか、間隔の意匠が変わるため。レイアウト費用は無視でき、CLS は 0.00001。
- 課題の終わりの霧（紙色）は約 0.3 画面残した。写真が紙に溶ける「間」で、0.6 画面の基準より短い。

## 7. 共有部分への依頼

1. **ヘッダーのスクロール処理**（`site-header.tsx`）：rAF 内の `window.scrollY` 読み取りが、HOME の変更後に残った強制レイアウト 72 回のうち 42 回。scroll イベント側で読むか IntersectionObserver に。
2. **HOME のガラス面**（`site-header.module.css` の `.header[data-brand][data-surface="glass"] .bar`）：電話では動く映像・WebGL の上で `backdrop-filter: blur(16px) saturate(1.3)` が毎フレーム掛かる（R4）。
   粗いポインター／1024 px 未満は blur なしの燻した塗りに（HOME の白い文字は 70%＋blur で 4.5:1 を測定済み。blur なしなら 78% 前後で再測定を）。
3. **ロゴの出現**：`data-brand="hidden"` → `"shown"` で `.brand` の opacity が瞬時に切り替わる。巨大な ADELVA が飛び込む瞬間なので、`.header[data-brand] .brand` に 0.2 s 前後の opacity 遷移を（R3）。
4. **他ページの先読み**：HOME でも `/media/adelva/about-a2/m-plate-0-853.avif`、`/media/adelva/approach/m-hero.webp`、CSS 2 本が「preload したが使っていない」と警告（電話で他ページの写真を読んでいる）。

## 8. 残課題

- **実機未確認**：iPhone Safari・Android の実 GPU での描画速度と見た目は見ていない（検証はすべて SwiftShader と Playwright WebKit）。特に 24 fps の静止中の描画、減衰の手触り、映像の開始の速さ。
- **電話の GPU メモリ**：同時には持たなくなったが、湖は単独で約 104 MB（契約 R5 の 64 MB を超える）。湖の板を電話（縦）のカメラが見る横幅に切り詰めた専用ファイルを作れば半分近くにできる見込み（タブレット横は全幅が必要なので別ファイル）。
- **画像のデコード回数**：trace の 8 ms 超のデコードは前後とも約 120 回。trace に URL が出ず特定できなかった（ラスタースレッド側。支援対象と支援領域の写真の拡縮で再デコードしている可能性）。
- **工程の目盛り**：幅の遷移（6 本・1 px）を残した（§6）。
- **ヘッダー関連**（§7）は共有担当の作業待ち。
- **残る強制レイアウト 35 回**（§3）：DOM API の読み取りではない。場面ごとに更新を止めて二分探索すれば特定できる。
- 写真の差し替えはなし（HOME の写真は実写として維持の決定どおり）。
